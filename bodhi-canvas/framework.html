Concept brief · Bodhi × Slingshot

Agentic Project Model

A way to describe an AI-driven workflow as an open knowledge graph, built from Anthropic's published guidance on agents, hooks, skills and evals, with AI-DLC as the lifecycle that fills it in. The canvas prototype is built on this model.

The shift

From a proprietary agent to an open graph any agent can use

Today

  • The platform's own agent runs the work
  • Requirements, prompts and tests live inside the tool
  • Clients can't bring the agents they already use
→

Proposed

  • The product is the project graph: requirements, stories, UI, data, agents, hooks, evals, KPIs
  • The graph is served over MCP and exported as Agent Skills, so Claude, Copilot, Bedrock or in-house agents can read and write it
  • The canvas is where people see and change it
The model

Four layers, one graph

Each layer is a view on the canvas. They share the same nodes, so a function in the UI view is the same function the agents handle in the Orchestration view. Selecting any node traces its lineage across all four.

Hooks, in plain language

Pick the moment, then the check

Non-technical users never see an event name. They choose when something should happen on a connection and what kind of check runs. The canvas maps that to the underlying hook.

On the canvasHook eventTypical use
Before this actionPreToolUseBlock a write to plan data until a person approves it
After this actionPostToolUseRedact PHI from a result, log to the audit trail
When work is handed offSubagentStart / SubagentStopCheck that the delegation brief is complete; check the subagent's result
When a task is marked doneTaskCompletedQuality gate: run the regression eval and reject on failure
When the agent finishesStopConfirm every required output exists before responding
When a session startsSessionStartLoad the client's plan context

Check types map to hook handlers: Rule or script (command), AI judge (prompt), Investigating agent (agent), External service (http), and Human approval (a permission decision of ask).

Lifecycle

AI-DLC fills the knowledge base

AI-DLC replaces sprints with short "bolts" and epics with "units of work". AI proposes, and the team validates the proposals together (mob elaboration). Each phase writes specific node types into the graph.

Inception

  • Requirements
  • User stories
  • KPIs
  • Units of work

Construction

  • UI, functions, data
  • Agents, skills, tools
  • Hooks and human checkpoints
  • Tests and eval tasks

Operations

  • Metrics against KPIs
  • Eval results over time
  • Production failures become new eval tasks
Open by default

How the graph stays agent-agnostic

  1. Property-graph core. Typed nodes and edges, stored in any graph store and queried with openCypher or GQL. Facts carry valid-from and valid-to times (the temporal approach used by Graphiti/Zep), so the graph records how the project changed.
  2. Portable serialization. JSON-LD export with a published vocabulary, so other knowledge graphs can link to it.
  3. MCP server. Tools such as graph.query, graph.get_lineage, graph.attach_hook and graph.record_eval let any MCP-capable agent read and update the project.
  4. Agent Skills export. Skill nodes become SKILL.md folders. Hooks become runnable hook config.

Open question for the team: which parts of Bodhi stay proprietary (governance, audit, connectors to client data) and which become the open layer (the schema, the MCP surface, the canvas).
